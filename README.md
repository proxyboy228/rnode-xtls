# rnode-xtls

Интерактивный генератор **скрытой Remnawave-ноды** (remnanode) со **скрытым
ядром Xray** — с **оригинальным, официальным** ядром из
[`XTLS/Xray-core`](https://github.com/XTLS/Xray-core).

Это исправленная версия оригинального `rnode.sh`: механизм маскировки и
функционал ноды не изменены, добавлены только фиксы (см. [Что
исправлено](#что-исправлено-относительно-оригинального-rnodesh)). Установка
кастомного ядра **опциональна** (по умолчанию — нет): если отказаться,
используется ядро Xray, уже вшитое в базовый образ `remnawave/node`.

> Есть парный репозиторий `rnode-jolymmiles` с тем же скриптом, но ядром из
> форка `Jolymmiles/Xray-core` (там ядро ставится всегда). Единственное отличие
> между репозиториями — источник ядра.

## Быстрый старт (curl)

Интерактивное меню:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/proxyboy228/rnode-xtls/main/rnode.sh)
```

Сразу указать команду:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/proxyboy228/rnode-xtls/main/rnode.sh) generate
```

Альтернатива через pipe (интерактивный ввод читается из `/dev/tty`):

```bash
curl -fsSL https://raw.githubusercontent.com/proxyboy228/rnode-xtls/main/rnode.sh | bash -s -- generate
```

> Замените `proxyboy228/rnode-xtls` на свой `<user>/<repo>`, если назвали
> репозиторий иначе. Для `curl`-запуска репозиторий должен быть **публичным**.

## Команды

| Команда    | Действие                                                       |
|------------|----------------------------------------------------------------|
| `generate` | Выбор варианта маскировки по категории (интерактивно)          |
| `random`   | Случайный вариант с возможностью «перебросить» (reroll)        |
| `check`    | Проверка зависимостей системы                                  |
| `clean`    | Удалить сгенерированные в текущей папке файлы                   |
| `help`     | Справка                                                         |

Без аргумента запускается главное меню.

## Требования

- `docker` + `docker compose` (или standalone `docker-compose`)
- `curl`, `unzip`
- `python3` **или** `jq` — только для онлайн-меню выбора версии ядра
  (без них версию можно ввести вручную)

## Что делает скрипт: общая логика

Скрипт **сам ноду не запускает как процесс** — он **генерирует набор файлов**
(Dockerfile, compose, entrypoint, `.env`), которые собирают и поднимают
remnanode в Docker так, чтобы её было трудно обнаружить по именам процессов,
файлов и контейнеров. Пошагово:

1. **Выбор «легенды».** В скрипте зашит словарь из ~100 вариантов — имён
   типичных системных демонов (`nginx`, `redis-server`, `postgres`, `traefik`,
   `dockerd`, …) с категориями. Ты выбираешь один (через `generate` по
   категориям или `random`). Выбранное имя — это то, во что будет
   «переодета» нода.
2. **Генерация файлов** в целевой директории (текущая или новая).
3. **Конфигурация `.env`** — порт ноды, порт API и секрет подключения к панели.
4. **(Опционально) кастомное ядро Xray** — скачать конкретную версию из
   `XTLS/Xray-core` и вшить её в образ. По умолчанию шаг пропускается, и
   берётся ядро из базового образа.
5. **Сборка и запуск** `docker compose up -d --build` (с авто-`sudo`, если
   нужно).

Схема потока:

```
main
 └─ show_main_menu / прямая команда (generate|random|check|clean)
     └─ выбор варианта (process = имя-маскировка)
         └─ create_variant_files(target_dir, variant)
              ├─ .Dockerfile          (generate_dockerfile)
              ├─ docker-compose.yml   (generate_docker_compose)
              ├─ docker-entrypoint.sh (generate_entrypoint)
              ├─ .env / .env.example  (generate_env_example)
              └─ bin/.keep            (заглушка для COPY; сюда же ляжет бинарник)
         └─ configure_env(target_dir)      # порты + секрет
         └─ setup_custom_core(target_dir)  # ОПЦИОНАЛЬНО: скачать ядро XTLS
         └─ docker compose up -d --build   # по желанию, сразу
```

## Генерируемые файлы и их роль

| Файл                  | Роль                                                                                          |
|-----------------------|-----------------------------------------------------------------------------------------------|
| `.Dockerfile`         | Собирает образ на базе `remnawave/node:latest`, переименовывает ядро и создаёт wrapper `rw-core`. |
| `docker-compose.yml`  | Описывает сервис: `network_mode: host`, `NET_ADMIN`, лимиты, healthcheck, проброс env из `.env`.  |
| `docker-entrypoint.sh`| Точка входа контейнера: рандомизирует имена сокетов/токенов, стартует supervisord.             |
| `.env` / `.env.example` | Параметры подключения: `EDGE_NODE_PORT`, `EDGE_API_PORT`, `EDGE_SECRET`.                     |
| `bin/`                | Папка сборочного контекста. Пустая (`.keep`) — если ядро не скачивали; с бинарником, названным как процесс (напр. `bin/nginx`) — если скачивали. |

> `.env` и `bin/` — в `.gitignore`, чтобы секреты и бинарник не попадали в репозиторий.

**Маскировка артефактов ядра.** Папка называется нейтрально (`bin/`, задаётся
переменной `CORE_DIR_NAME`), а бинарник внутри — именем «легендного» процесса
(напр. `bin/nginx`), не `xray-core/xray`. Плюс из папки не остаётся лишних
`geoip.dat`/`geosite.dat`/`LICENSE`/`README.md` от релиза Xray — только сам
бинарник. Папка нужна для сборки/пересборки, поэтому её можно не удалять.

## Как устроена «скрытость»

Маскировка складывается из четырёх независимых приёмов; **функционал Xray при
этом не меняется** — меняются только имена, которые видит наблюдатель.

**1. Переименование бинарника ядра.** В `.Dockerfile`:

```dockerfile
mv /usr/local/bin/xray /usr/local/bin/<process>     # напр. /usr/local/bin/nginx
```

Файл ядра больше не называется `xray`.

**2. Подмена имени процесса (`argv[0]`).** Создаётся wrapper `rw-core`:

```sh
#!/usr/bin/bash
exec -a "<process>" /usr/local/bin/<process> "$@"
```

`exec -a "<process>"` запускает ядро так, что в `ps`, `/proc/<pid>/comm` и
подобном оно выглядит как `nginx` (или другой выбранный демон), а не `xray`.
Именно поэтому shebang — **bash**, а не `sh`: `exec -a` есть в bash, но нет в
dash (`/bin/sh`), см. [Что исправлено](#что-исправлено-относительно-оригинального-rnodesh).

`rw-core` — это стабильное имя, которое дёргает supervisord ноды; путь к
реальному бинарнику передаётся через `ENV RW_CORE_BINARY=/usr/local/bin/<process>`.

**3. Рандомизация внутренних имён.** В `docker-entrypoint.sh` на каждый старт
генерируются случайные:

- `SUPERVISORD_USER`, `SUPERVISORD_PASSWORD`, `INTERNAL_REST_TOKEN` (по 64 símv.);
- префикс unix-сокета вместо предсказуемого `remnawave-internal`:
  `INTERNAL_SOCKET_PATH=/run/<random8>-<random10>.sock`.

Так по именам сокетов/токенов ноду тоже не опознать.

**4. Маскировка на уровне Docker.** `docker-compose.yml` называет сервис,
контейнер (`svc_<name>`), hostname (`svc-<process>`) и OCI-лейблы образа под
выбранный «системный сервис». Пустые `image.url/source/documentation` убирают
следы происхождения.

## Логика кастомного ядра

Шаг **опционален** (`Install custom Xray core? [y/N]`, по умолчанию N). Если
отказаться — используется ядро из базового образа `remnawave/node`. Если
согласиться:

1. **Определение версии** (`resolve_xray_version` / `select_xray_version`):
   - `latest` — самый новый релиз (включая pre-release);
   - `stable` — последний стабильный (`/releases/latest`);
   - конкретный тег (напр. `v26.6.27`) — вручную или из меню.
   Меню строится парсингом GitHub Releases API через `python3`/`jq`.
2. **Определение архитектуры** (`get_xray_arch`): `uname -m` → имя ассета
   (`64`, `arm64-v8a`, `arm32-v7a`, `riscv64`, …).
3. **Скачивание** `Xray-linux-<arch>.zip` из релизов `XTLS/Xray-core`.
4. **Проверка целостности**: если доступен `.dgst`, из него берётся SHA-256 и
   сверяется с `sha256sum` скачанного архива. При несовпадении — отказ.
5. **Распаковка и проверка запуска**: извлекается `xray`, выполняется
   `xray version` — бинарник должен быть работоспособным.
6. **Встраивание**: бинарник кладётся в `bin/` под именем процесса, и при
   `docker build` строка `COPY bin/ /tmp/bin/` вносит его в образ, где `.Dockerfile`
   заменяет им штатное ядро перед переименованием.

Кроме сборочного пути, есть **рантайм-override**: если задать переменную
`CUSTOM_CORE_URL`, entrypoint скачает ядро по этому URL при старте контейнера
(удобно для быстрой подмены без пересборки).

## Как нода запускается внутри контейнера

1. Docker запускает `docker-entrypoint.sh`.
2. Скрипт чистит устаревшие сокеты, генерирует случайные креды/пути, экспортирует
   их и стартует `supervisord -c /etc/supervisord.conf` в фоне.
3. Если задан `CUSTOM_CORE_URL` — ядро скачивается в `RW_CORE_BINARY`.
4. Проверяется версия ядра: `rw-core version` → в лог.
5. `exec "$@"` передаёт управление основной команде образа (процессы ноды под
   supervisord). Healthcheck в compose проверяет `pidof node`.

Подключение к панели Remnawave задаётся через `.env`:

| Переменная         | Назначение                                  |
|--------------------|---------------------------------------------|
| `EDGE_NODE_PORT`   | порт ноды (compose → `NODE_PORT`)           |
| `EDGE_API_PORT`    | порт XTLS API (compose → `XTLS_API_PORT`)   |
| `EDGE_SECRET`      | секрет ноды (compose → `SECRET_KEY`)        |

## Что исправлено относительно оригинального rnode.sh

- **Wrapper `rw-core` использует `#!/usr/bin/bash`, а не `#!/bin/sh`.**
  `exec -a <name>` — bash-изм; под dash (`/bin/sh` в образе) он падает с
  `exec: -a: not found`, из-за чего ядро Xray не стартует
  (`Xray core failed to start`). С bash-shebang маскировка `argv[0]` работает,
  и ядро поднимается.
- **Авто-`sudo` для docker.** `get_docker_sudo()` добавляет `sudo` к
  `docker compose`, если пользователь не root и не в группе `docker` — иначе
  `permission denied … /var/run/docker.sock` при `up`. Под root или при
  доступе к сокету напрямую — sudo не добавляется.
- **Устойчивый резолвинг версии.** Разбор GitHub Releases корректен и для
  «красивого», и для компактного (однострочного) JSON.

## Диагностика

```bash
# зависимости
bash rnode.sh check

# логи запущенного контейнера (sudo — если ты не в группе docker)
sudo docker compose logs --tail 100

# проверить wrapper внутри контейнера
sudo docker compose exec <service> head -n1 /usr/local/bin/rw-core   # ожидаем #!/usr/bin/bash
sudo docker compose exec <service> rw-core version                   # ожидаем "Xray ..."
```

Признак незакрытого фикса `exec -a`: в логах `rw-core: exec: -a: not found`.
В этой версии он устранён на этапе генерации `.Dockerfile`.
